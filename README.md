# ДОМАКС (DOМАКС) — Сервис взаимодействия жителей с управляющей компанией в MAX

Сервис управления домом и подачи заявок в управляющую компанию, встроенный в мессенджер MAX (мини-приложение / WebApp).

---

## 1. Назначение решения

ДОМАКС автоматизирует коммуникацию между жителями многоквартирных домов (МКД) и управляющей организацией (УК). Решение решает проблемы потери заявок, отсутствия прозрачности по регламентным срокам устранения аварий и исключает дублирование обращений от соседей за счёт механизма коллективного апвоута («У меня так же»).

---

## 2. Основной пользовательский сценарий

1. **Житель (RESIDENT)**:
   - Входит в мини-приложение через бота мессенджера MAX или через служебный экран выбора роли (`/dev/role`).
   - На главной странице видит адрес своего дома, актуальные объявления УК («Плановое отключение воды») и последние заявки.
   - Подаёт заявку: вводит тему, описание (категория определяется автоматически эвристическим классификатором, с возможностью переопределить вручную), указывает подъезд/этаж и прикрепляет фото.
   - Отслеживает SLA-таймер до дедлайна устранения и статус заявки (`CREATED` → `IN_PROGRESS` → `COMPLETED` → `CLOSED`).
   - В общей ленте дома видит заявки соседей по своему адресу и может нажать «У меня так же», повышая приоритет проблемы без создания дублей.

2. **Диспетчер УК (DISPATCHER)**:
   - Переходит в панель диспетчера (`/dispatcher`) — либо со служебного экрана выбора роли, либо по кнопке «Панель администратора» в боте.
   - Видит очередь всех заявок, отсортированную по близости SLA-дедлайна.
   - Переводит заявку в работу (`IN_PROGRESS`), отмечает выполненной (`COMPLETED`), закрывает (`CLOSED`).
   - Публикует и удаляет общедомовые объявления, которые видят все жители на главной.

## 3. Состав и архитектура решения

```
[ Клиент MAX / Браузер ]
            │
            ▼ HTTPS (443)
┌───────────────────────────────────────────────────────────┐
│  Caddy (реверс-прокси, автоматический SSL через Let's      │
│  Encrypt, публичный адрес *.sslip.io)                      │
└───────────────┬───────────────────────────┬────────────────┘
                │ /api/*                    │ /*
                ▼                           ▼
┌──────────────────────────────┐   ┌──────────────────────────────┐
│  Backend (NestJS + TS)       │   │  Frontend (React + Vite)     │
│  Port: 3000                  │   │  Port: 5173                  │
└───────────────┬──────────────┘   └──────────────────────────────┘
                │ TypeORM / SQL
                ▼
┌──────────────────────────────┐
│  PostgreSQL 16 Alpine        │
│  Port: 5432 (внутр.)         │
└──────────────────────────────┘
```

- **Frontend**: React 18, TypeScript, Vite, React Router 6, собственная дизайн-система (токены, bottom sheets, адаптивные компоненты), интеграция с MAX Bridge (`window.WebApp`: `initData`, `BackButton`, `HapticFeedback`).
- **Backend**: NestJS, TypeScript, TypeORM, Swagger/OpenAPI 3.0, JWT-аутентификация с проверкой подписи `initData` мессенджера MAX (HMAC-SHA256).
- **База данных**: PostgreSQL 16 Alpine.
- **Инфраструктура**: Docker Compose; на боевом VPS — Caddy 2 как реверс-прокси с автоматическим выпуском SSL-сертификата (Let's Encrypt) на публичном адресе `*.sslip.io`. Локальный запуск (раздел 4) поднимает только frontend/backend/БД без Caddy — HTTPS для него не требуется.

## 4. Быстрый запуск одной командой через Docker

### Требования
- Docker Engine 24.0+
- Docker Compose v2+

### Запуск

```bash
docker compose up --build
```

Сборка и старт всех сервисов занимает около 1–2 минут. После старта:
- Фронтенд: `http://localhost:5173`
- API: `http://localhost:3000/api`
- Swagger UI: `http://localhost:3000/api/docs`

## 6. Переменные окружения (.env)

Файл `.env` создаётся в корне репозитория, рядом с `docker-compose.yaml` (не коммитится в git).

Шаблон — `backend/.env.example`:

```ini
# Секрет для подписи JWT-токенов сессий
JWT_SECRET=change-me-in-production

# Токен бота MAX — нужен для проверки HMAC-подписи initData (POST /api/auth/max).
# Для локальной разработки и демонстрации жюри можно оставить как есть:
# основной сценарий проверяется через dev-login (см. раздел 10), где этот токен не используется.
MAX_BOT_TOKEN=your-bot-token-from-max-platform
```

Корневой `.env` (для `docker-compose.yaml`):

```ini
JWT_SECRET=domax-dev-secret-change-me
MAX_BOT_TOKEN=dev-placeholder-token
```

Прочие параметры (адрес БД, порты, `VITE_API_URL`) уже заданы значениями по умолчанию в `docker-compose.yaml` и не требуют правки для локального запуска.

## 8. Внешние сервисы и интеграции

- **MAX WebApp Bridge** (`window.WebApp`, скрипт `max-web-app.js`): получение `initData` пользователя, управление системной кнопкой «Назад», haptic-обратная связь. Вне клиента MAX (обычный браузер) эти вызовы просто не выполняются — приложение переключается на альтернативный вход (см. раздел 9).

## 9. Порядок работы с тестовыми данными и режим для жюри

Проект работает как в реальном клиенте MAX (вход по подписанной `initData`), так и вне его — для тестирования и демонстрации жюри.

**Механика для жюри — `POST /api/auth/dev-login`.** Мгновенно выдаёт валидный JWT под нужной ролью без прохождения полноценной авторизации MAX:

```bash
curl -X POST http://localhost:3000/api/auth/dev-login \
  -H "Content-Type: application/json" \
  -d '{"role": "RESIDENT"}'
```

`role` — `"RESIDENT"` или `"DISPATCHER"`.

На фронтенде это доступно через служебную страницу выбора роли — `http://localhost:5173/dev/role`, а также через ссылку «Демо: сменить роль» на главном экране.

**Это осознанное решение, а не пробел в безопасности**: `dev-login` существует специально, чтобы жюри не нужно было заводить два разных аккаунта MAX для проверки обоих ролевых сценариев. Ручка не предназначена для боевого использования вне хакатона.

При первом запуске база данных пустая — все пользователи и заявки создаются по ходу тестового сценария (см. раздел 10). Схема БД создаётся автоматически через TypeORM (`synchronize: true`).

## 10. Пошаговый сценарий проверки

### Вариант A — публичный боевой сервер (без установки чего-либо)

- Приложение: **https://domax.46.29.167.230.sslip.io**
- Swagger UI: **https://domax.46.29.167.230.sslip.io/api/docs**

Дальше сценарий идентичен варианту B, начиная с шага 3 — просто откройте указанный адрес вместо `localhost:5173`.

### Вариант B — локальный запуск

1. Запустите проект: `docker compose up --build`.
2. Откройте `http://localhost:5173`.
3. При первом входе (вне клиента MAX) откроется экран/переключатель выбора роли — выберите **«Войти как житель»**. Приложение получит JWT через `dev-login` с ролью `RESIDENT`.
4. На главной странице задайте адрес и квартиру (первый раз — по кнопке с адресом откроется форма; сохраняется через `PATCH /api/users/me`).
5. Нажмите «+» и создайте заявку:
   - Тема: «Течёт потолок в ванной»
   - Описание: «Вода с соседнего этажа, сильно капает»
   - Категория подставится автоматически («Сантехника»), можно изменить вручную
   - Укажите подъезд/этаж (опционально)
   - Отправьте заявку.
6. Откройте созданную заявку — виден расчётный SLA-дедлайн (конкретная дата и время) и статус «Зарегистрирована».
7. Перейдите на `http://localhost:5173/dev/role` и переключитесь на роль **«Диспетчер»**.
8. Откройте панель диспетчера (`/dispatcher`):
   - Увидите созданную заявку в общем списке
   - Переведите её в статус «Взять в работу» (`IN_PROGRESS`), затем «Отметить выполненной» (`COMPLETED`)
   - Опубликуйте тестовое объявление в форме «Новости дома» (заголовок + текст)
9. Переключитесь обратно на роль «Житель» — на главной странице появится опубликованное объявление, а в заявке — обновлённый статус.
10. В любой момент проверить API напрямую можно через Swagger UI: `http://localhost:3000/api/docs` локально или `https://domax.46.29.167.230.sslip.io/api/docs` на боевом сервере (кнопка **Authorize** принимает JWT, полученный на шаге 3 или 7).

## 11. Примеры ожидаемого поведения системы

- **Расчёт SLA**: при создании заявки бэкенд сразу вычисляет `slaDeadline` — конкретный момент времени дедлайна, а не число часов, — по справочнику нормативных сроков в зависимости от категории (авария по сантехнике/лифту — короче, электрика/общие зоны — дольше).
- **Фильтрация по дому**: список заявок на главной и в разделе «Заявки» фильтруется по адресу текущего пользователя — житель видит проблемы только своего дома.
- **Коллективный апвоут**: повторное нажатие «У меня так же» увеличивает счётчик `upvotesCount` заявки, не создавая новую запись — так диспетчер видит масштаб проблемы без завала одинаковыми заявками.
- **Ролевой доступ**: попытка вызвать ручку диспетчера (например, смену статуса) под ролью жителя вернёт `403 Forbidden` — доступ проверяется на бэкенде через JWT независимо от интерфейса.

## 12. Известные ограничения MVP

- **`dev-login`** — намеренный временный вход для тестирования и демонстрации жюри (см. раздел 9), не предназначен для продакшена.
- **Адрес пользователя** — заполняется вручную через профиль (`PATCH /api/users/me`), без интеграции с ФИАС/ГИС ЖКХ; при первом входе стоит значение-заглушка.
- **Фото к заявке** — принимается как готовая ссылка (`photoUrl`), полноценного файлового хранилища (S3 и т.п.) в MVP нет.
- **Классификация категории по описанию** — эвристика по ключевым словам на фронтенде, а не серверная ML-модель; пользователь всегда может скорректировать категорию вручную.
- **Уведомления в чат MAX при смене статуса заявки** — не реализованы в текущей версии (требуют интеграции с MAX Bot API и токена бота).
- **Валидация `initData`** — полностью реализована по официальному алгоритму MAX (HMAC-SHA256), но не проверялась вживую с реальным ботом на момент сдачи из-за отсутствия боевого `MAX_BOT_TOKEN` на этапе разработки.
